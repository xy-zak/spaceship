Architecture

One process on pA serves the app, keeps track of turns, and passes model calls through to Ollama, which only listens on localhost. The station whose turn it is runs the full editor. The other two show a light view page, and the stations swap pages when OK is pressed.

  • The active station runs today's editor, with its mouse handling replaced by panel actions. Moving generation onto the server would mean rewriting main.ts, which is tangled up with on-screen layout.
  • Server to stations uses Server-Sent Events, and stations to server use plain POST. Both are built into Node and the browser, so there is no WebSocket library to add.
  • On a turn change each Pi swaps pages with location.replace. That costs about a second, and clears all editor state every turn, which helps a Pi 4 that runs for hours.
  • Ollama never listens on the LAN. Stations reach it only through the same-origin /ollama proxy, so there is no CORS setup and no open model port.

One turn

What happens from the moment pC's turn starts until pD takes over.

The shared document

pC's view of the manifesto in round one. The opening is locked. pB's turn is the last one, so pC may cut into it. Everything past the knob is text the model has written ahead, which becomes part of the turn only if the knob moves over it.

When pC presses OK

  1. pC sends only the text after the floor. It never sends the floor, so a station bug cannot change locked turns.
  2. The words at the start that match pB's turn stay credited to pB: "teach doubt before style. Every brief should end".
  3. The rest becomes pC's turn: "with a question the client did not ask."
  4. pD's floor is now the opening plus pB's kept words. pD may cut into pC's turn, nothing older.

If only the opening exists, the opening is the whole floor, so it can never be rewritten.

// manifesto.json after pC presses OK
{
  "active": "D",
  "turns": [
    { "station": "opening", "text": "Design education must" },
    { "station": "B", "text": "teach doubt before style. Every brief should end" },
    { "station": "C", "text": "with a question the client did not ask." }
  ]
}

Steering

The app already builds a menu of steering dimensions after every pause in scrubbing, from the text up to the knob and the phrases in the attention boxes. The plan keeps that flow and changes what goes into it: a manifesto catalog, slots the model fills from the text, and one lens line per station.

Orange rows are slots the model fills with the manifesto's own words. Station hardware

Each function names the action it needs instead of a part. Any part that behaves like its action type works, so the panel can be built from whatever fits. One part can carry two types: an endless dial that also presses gives one endless and one trigger.

Action types
Type What the hand does Sends Rules Parts that fit
Endless Turns or scrolls with no end stops. Only the movement counts. signed steps since the last line Report relative steps at any speed, never a position. rotary encoder, jog wheel, scroll wheel, trackball axis
Trigger Presses and lets go. Nothing stays pressed. one word per press Debounce, and fire once on press. push button, arcade button, an encoder's press, capacitive pad, foot switch
Capped Moves between two hard ends and stays where it is left. position 0–1000 Calibrate both ends and smooth the reading. Send only after a move of 20 or more, or noise will restart generation over and over. Exactly 0 and 1000 are always sent, so both ends are reachable. No spring return, and the 0 end must be easy to find. slide potentiometer, end-stopped rotary potentiometer, fader
Hold Presses and keeps holding. Letting go early cancels. one word when the hold completes Fire only after 1 s of continuous hold, so nobody passes the turn by accident. Show progress if you can, e.g. with an LED. large push button, key switch, any trigger part

No function needs a switch that stays flipped. Every on/off state lives on screen and resets when the editor loads each turn, so a latching switch would drift out of step with it. Use a trigger instead.

Per station that makes 3 endless, 3 triggers, 1 hold, and per steering channel a capped slider and an endless encoder. The select trigger can be the press of the along-the-line dial.

Every function the editor has, its action type, and the line the ESP32 sends:

Word cursor

Choosing important words works like moving through a text grid. Two endless controls move a highlighted word, and the select trigger boxes it.

  • The cursor starts on the last shown word at the start of each turn.
  • It moves over all shown text, locked turns included, because boxing a word only steers and never edits.
  • It stops at the main knob, and moves back with the knob when scrubbing cuts past it.
  • On a word inside a box, that box highlights, the model's boxes included.
  • Select makes the cursor's word the keyword and stretches the box up to 3 words each side, stopping at punctuation (. , ; : ! ?). The box has the same shape as the model's boxes, so the prompt gets the keyword in context. Pressing select anywhere inside a box removes it. 
# ESP32 → browser · 115200 baud · one line per event
scrub -3          # endless · main knob, signed steps
across 1          # endless · word cursor along the line
down -1           # endless · word cursor between lines
select            # trigger · box the phrase at the cursor, or unbox it
box               # trigger · model's boxes on/off
reroll            # trigger
value 1 734       # capped · channel 1 direction, 0–1000
strength 1 2      # endless · channel 1 strength, signed steps
ok                # hold · once the 1 s hold completes

Firmware rules

  • The browser only sees the lines, so any part works as long as its firmware follows the rules of its action type.
  • In setup(), print an empty line, the marker # spaceship-panel 1, then every capped position. The browser resets the board right after opening the port and ignores lines until the marker, so this syncs the panel on every page load. Lines starting with # are comments.
  • Steering channels are numbered from 1. Add a channel by adding a slider and an encoder; the browser opens its knob when the channel is first touched.
  • Each channel takes three pins, one ADC1 pin for the slider and two for the encoder, so the reference board has room for 2 channels.

The browser reads the port as a cancellable stream of lines in src/input/serial.ts. A keyboard version of the same events stands in during development.

Server API

A Vite plugin adds these routes to both the dev server and vite preview. "Tail" means the text after the floor. The server keeps the turns in memory and writes them to manifesto.json on every commit, through a temporary file and a rename.

Route Who Body Effect
GET /api/events every station none SSE stream. state on connect and after each commit; live while the active station edits.
POST /api/live active station station, tail, steering Relayed to the views as live. Not saved.
POST /api/commit active station station, tail Splits the last turn, appends the new one, moves to the next station, saves, sends state.
POST /api/skip pA only none Passes the turn if a station is stuck.
POST /api/reset pA only none Renames the file with a date and starts again from the opening.
/ollama/v1/chat/completions active station chat completion Proxied to 127.0.0.1:11434. Nothing else on Ollama is reachable.

Posts from a station whose turn it isn't are refused. Skip and reset accept requests from localhost only, so the facilitator runs them with curl on pA.

Two settings the server can't work without: allowedHosts: ["pa.local"], because Vite refuses any other host name, and an Origin header set on the proxy, because Ollama refuses origins it doesn't know.

Model on pA

  • src/llm/cerebras.ts becomes src/llm/ollama.ts. The URL becomes /ollama/v1/chat/completions, the API key goes, and max_completion_tokens becomes max_tokens. The streaming parser stays.
  • The model name is one constant in src/stations.ts. If you switch to a model without reasoning, drop reasoning_effort, which Ollama may reject.
  • live-realization.ts asks for n: score from 0 to 10 per sentence. Confidence is score / 10, and a knob pins at 0.8 as before.
  • Lower BUFFER_WORDS from 300 to about 150, since every steering change throws the buffer away.
# Ollama environment on pA
OLLAMA_NUM_PARALLEL=4      # boxes and pinning don't queue behind the text
OLLAMA_KEEP_ALIVE=-1       # keep the model loaded between turns
OLLAMA_CONTEXT_LENGTH=16384

# the app, turns and proxy
npm run build
npx vite preview --host --port 4173

Pi setup

// /etc/chromium/policies/managed/spaceship.json
{
  "OverrideSecurityRestrictionsOnInsecureOrigin": [
    "http://pa.local:4173"
  ],
  "SerialAllowUsbDevicesForUrls": [{
    "devices": [{ "vendor_id": 4292 }, { "vendor_id": 6790 }],
    "urls": ["http://pa.local:4173"]
  }]
}
  • Web Serial only works on secure pages, and plain http from pA isn't one. The first entry tells Chromium to treat pA as secure.
  • The second grants the serial port without a prompt, which matters with no mouse. 4292 is the CP2102 USB chip's vendor and 6790 the CH340's; check yours with lsusb.
  • Give pA a fixed IP or the pa.local name.
  • No mouse or keyboard is attached. The page hides the pointer and ignores clicks, so a stray mouse does nothing.
# one per Pi; station=C and station=D on the others
chromium --kiosk --noerrdialogs --autoplay-policy=no-user-gesture-required \
  "http://pa.local:4173/spaceship/?station=B&live=true"

The autoplay flag lets the sound engine start. Today it only unlocks on a pointer or key press, and serial input never sends one.

Build order

  1. Spike, half a day: one Pi 4, one ESP32, the policy file, and a 15-line page on pA that prints serial lines. Also curl Ollama's endpoint. Done when lines appear on the Pi with no prompt and isSecureContext is true.
  2. Ollama, manifesto content and the panel actions on one machine, driven by the keyboard stand-in. The mouse code goes in this step. Done when text streams, the word cursor boxes words, the fan offers manifesto dimensions with filled slots, knobs pin, and npm run build passes.
  3. Turns: the plugin, the view page, and seed, floor and commit in the editor. Done when three tabs pass turns with the keyboard OK, the commit-split test passes, and a server restart keeps the manifesto.
  4. One real panel: swap the keyboard stand-in for Web Serial on the laptop. Done when one ESP32 runs a full turn with no keyboard. Localhost counts as secure, so no flags are needed there.
  5. Pis: kiosk, policies, and a speed check. Done when a fake 5,000-word manifesto scrubs smoothly on a Pi 4. If it doesn't, redraw at most once per frame.

Risks

  1. Pi 4 drawing speed as the manifesto grows. The editor shows only recent text; step 5 measures it.
  2. Local generation is slower than Cerebras, by roughly 10× on a rough estimate, so the realtime feel weakens. A smaller buffer helps.
  3. gpt-oss:20b running prompts tuned for a 120b model writing stories, slot filling most of all. Test with the dev script before settling the panel.
  4. The Chromium policies are unverified on Raspberry Pi OS. Step 1 settles that.
  5. Noise on capped controls can restart generation over and over. The move-of-20 rule is required.
  6. Uncommitted work is lost if a Pi reloads mid-turn. Committed turns are safe on pA.
  7. The repo's origin is the upstream project. Fork it before committing; it is MIT licensed, so keep the notice.
